# 0003 /app/ の認証を Supabase Auth のログインにする

- 日付：2026-11-05

## 背景

/app/（カラ美）の `app-data`・`app-chat` は、ESP32 と同じ `x-device-key`
で認証している。これには2つの問題がある（#10）。

- ブラウザから送るには、デバイスキーを `VITE_DEVICE_KEY`
  に入れるしかない。`VITE_` の変数は配る JS
  に埋め込まれるので、サイトを開いた人なら誰でもキーを読める。読めた人は、センサー値の偽装や会話ログの読み書きができる
- 1回のビルドで鉢を1つしか扱えない。鉢が2〜3個になると、鉢ごとにビルドを分けるか、「誰がどの鉢を見てよいか」をサーバーで確かめる必要がある

## 決定

- 11/20 の発表と見学会は C（展示用に機能を絞る）にし、ログイン（A）は 11/20
  のあとに作る（#10 で決めた）
- A は次の形にする
  1. ユーザーは Supabase Auth でログインする
  2. ユーザーと鉢を `device_members`
     テーブルで結ぶ。1人が複数の鉢を持ち、1つの鉢を複数人で見られるよう、多対多にする
  3. /app/ は、ログインで得たアクセストークンを `Authorization`
     ヘッダーに付け、見たい鉢の `device_id` を本文に入れて送る
  4. `app-data`・`app-chat` は、トークンからユーザーを確かめ、`device_members`
     にそのユーザーと鉢の組があるときだけ答える
  5. `app-data` に「自分の鉢の一覧」を返す action を足し、アプリで鉢を切り替える
  6. A ができたら、`app-data`・`app-chat` の `x-device-key` と、/app/ の
     `VITE_DEVICE_KEY` を消す。デバイスキーは ESP32 だけが使う
- ESP32 の認証（`devices.device_key`）と LINE
  の紐付け（`devices.line_user_id`）は変えない
- 先に `device_members` のマイグレーションだけを入れる。関数と /app/ は 11/20
  のあとに変える

## 理由

- マイグレーションを先、関数のデプロイを後にするルールに合わせ、テーブルだけを先に入れる。テーブルを足すだけなので今の動きは変わらず、機能凍結（11/10）の前でもデモを壊さない
- `device_members` は `auth.users` の id だけを持つ。ログイン方法（メール、LINE
  ログインなど）を後で決めても、テーブルを作り直さなくてよい
- RLS のポリシーは作らず、ほかのテーブルと同じく Edge
  Functions（service_role）で確かめる。ブラウザから DB
  を直接読む経路を作らないので、権限を確かめる場所が関数の中に収まる
- 鉢が2〜3個のうちは、ユーザーと鉢の組を SQL で手で入れれば足りる。QR
  からの初回設定は、そのあとで足す

## 決めていないこと（11/20 のあと）

- ログイン方法：メールのマジックリンク、メールとパスワード、LINE
  ログインなど。LINE ログインなら `line_user_id` とつなげられるが、Supabase Auth
  で使えるかを確かめる必要がある
- 新規登録を開けるか：最初は登録を閉じ、メンバーだけを招待すれば、鉢が2〜3個のうちは足りる
- トークンの確かめ方：Supabase のドキュメント（2026-11 時点）は、
  `@supabase/server` の `withSupabase({ auth: "user" })` か
  `supabase.auth.getClaims()`
  を勧めている。前者は依存が増えるので、実装するときに今の版を確かめて選ぶ
- `verify_jwt`：ドキュメントは、ユーザー向けの関数では有効にしておくよう勧めている。`app-data`・`app-chat`
  は今 `false` なので、A で `true` に戻すかを決める
- 持ち主と家族で権限を分けるか（設定の変更を持ち主だけにする、など）：要るようになったら
  `device_members` に列を足す
- 同じ LINE ユーザーが鉢を2つ以上持つと、`line-webhook` の `.maybeSingle()`
  がエラーになり、LINE に返事ができない。どの鉢が返事をするかを決める必要がある

## 代替案

- B（アプリ用に別のキーを発行する）：キーをブラウザに置く点は変わらず、読めた人は誰でもその鉢を見られる。鉢ごとにキーを配る手間もある
- 鉢ごとに /app/
  をビルドする：鉢が増えるたびにビルドとデプロイが要り、キーが読める問題も残る
- `devices` に持ち主の列を足す（1つの鉢に1人）：1つの鉢を家族で見られない
- RLS のポリシーで、ブラウザから DB
  を直接読ませる：権限を、関数とポリシーの2か所で確かめることになる。今のテーブルはすべて全拒否で、関数だけが読む形にそろっている
