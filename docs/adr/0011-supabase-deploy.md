# 0011 Supabase のデプロイを、承認つきの GitHub Actions にする

- 日付：2026-11-08

## 背景

- 画面は Vercel が main から自動で出すが、マイグレーションと Edge Functions
  は中村が手元の PC から手で入れている（#14）
- 地引のアカウントからは本番のプロジェクトが見えないので、反映はいつも中村に頼むことになる
- 「`_shared/`
  を変えたら全部の関数を入れ直す」「マイグレーションを先に」を毎回手で守っている。マージしても、手で入れるまで本番では効かない（#68
  など）

## 決定

- workflow `supabase-deploy` を足す。main に `supabase/`
  の変更が入ったら動く（Actions の画面から手でも動かせる）
  - `plan`：`supabase db push --dry-run` の結果と、入れ直す関数を、実行の
    Summary に書き出す
  - `deploy`：GitHub の Environments の `production`
    で承認を待ち、マイグレーション → 全部の関数の順に入れる。main
    のときだけ動く（手で動かすときは、ほかのブランチも選べるため）
- 鍵（`SUPABASE_ACCESS_TOKEN`・`SUPABASE_DB_PASSWORD`）は GitHub の Secrets
  に、プロジェクトの ref は Variables に置く。鍵が無いあいだは飛ばして終わる
- Supabase CLI は 2.122.1 に固定する
- pg_cron
  の登録と、関数の環境変数（`supabase secrets set`）は対象にしない。今までどおり手で入れる

## 理由

- 承認の前に dry-run
  を読めるので、「中身を見せ、確認を取ってから入れる」を保てる
- 承認はリポジトリの画面でできるので、本番のプロジェクトが見えない地引でも反映できる
- いつも全部の関数を入れ直せば、`_shared/` の入れ忘れが起きない
- CLI 3.0 は 11/6 に出たばかりで、オプションの名前が変わった（`--project-ref` →
  `--remote`）。2.x の安定版で動くことを確かめてから上げる

## 代替案

- 承認なしで、マージしたらすぐ入れる：dry-run
  を読む機会がなくなる。マイグレーションは元に戻しにくい
- PR の時点で dry-run を出す：PR のたびに本番の DB
  へつなぐことになり、鍵を使う場面が増える
- 変わった関数だけ入れる：`_shared/`
  を使う関数をたどる必要があり、間違えると古いコードが残る
- 手作業のまま：上の背景のとおり
